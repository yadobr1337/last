# Исправления 1VPN

Изменения подготовлены в локальной ветке `audit/production-hardening` от исходного коммита архива `3bfebc4`. Существующая схема посуточной оплаты и общий визуальный стиль сохранены.

## Финансы

- `src/lib/yookassa.ts` изменяет платёж, баланс и проводку в одной транзакции SQLite. Webhook получает состояние по API магазина, проверяет заказ, получателя, сумму, валюту, признак тестового платежа и статус. Просроченные локальные ожидания сверяет фоновая задача.
- `src/lib/billing.ts` закрывает время по старому тарифу перед изменением лимита устройств или базовой цены. Биллинг использует целые копейки и сохраняет дробный остаток для следующего расчёта. Подарок учитывает лимит устройств. Повтор отправки одной формы подарка обрабатывает только пользователей без проводки этой операции.
- Демо-пополнение доступно в режиме разработки при явном флаге. В production тестовые ответы ЮKassa также отклоняются.

## Фоновые задачи и инфраструктура

- Фоновый биллинг выбирает просроченные записи пакетами. Очередь VPN хранится в SQLite. Аренды ограничивают параллельную обработку между процессами, а версия состояния защищает результат от записи поверх более свежего запроса.
- Remnawave сверяет имя пользователя при потере результата создания и повторяет синхронизацию после ошибки. При обновлении существующего профиля сохраняется выданная ссылка. Истечение и бан переводят доступ в отключённое состояние.
- Закупка Aeza резервирует одну попытку до обращения к API. Работа учитывает лимит количества, бюджет и цену котировки. Неопределённый заказ сверяется с инвентарём. Если подтверждения нет, запись остаётся в `ORDER_UNCERTAIN` до сверки. Для платного запуска из админки нужно подтверждение. Формат цены подтверждён в тесте с моками и требует сверки по ответу реального аккаунта на стенде.
- Уведомление резервируется до отправки в Telegram. Очередь ограничивает количество попыток, фиксирует отказы и отображает их в админке. При потере HTTP-подтверждения возможна повторная доставка. Количество и стоимость заказов, изменения ролей доступа, операций баланса и перезапусков фиксируются в локальных журналах приложения.

## Доступ и интерфейс

- JWT сверяет доступ с текущим пользователем. Бан, удаление учётной записи и смена пароля инвалидируют авторизацию. Telegram подписывает данные входа, проверки срока и одноразовости выполняются перед привязкой или входом. Одноразовые email-коды хранятся как HMAC, ограничены по времени и попыткам, погашаются вместе с изменением аккаунта.
- Главная выводит тарифы с сервера, а изменение цены отображается при следующем заходе. Изображение первого экрана загружается с высоким приоритетом. Персональный рендеринг сохраняется для входа и режима обслуживания.
- Nginx ограничивает частоту обращений к аутентификации и исключает платёжный webhook из access log. Проверка HTTPS проверяет сертификат. Шаблон новых нод убирает debug и Xray access log. Текст главной описывает подтверждаемое свойство шифрования подключения.

## Проверки и оставшиеся работы

- Тесты используют временную SQLite и ответы внешних сервисов из фикстур. Отдельная HTTP-проверка запускает собранный Next.js локально. Результаты команд приведены в [TEST_RESULTS.md](TEST_RESULTS.md).
- Для существующей SQLite нужны проверка структуры исходной базы, резервная копия и пробный запуск миграции. Для исторических платежей предусмотрена сверка, поскольку старые записи уже могли попасть в разрыв между начислением и статусом. [Порядок обновления](DEPLOYMENT_CHECKLIST.md).
- На стенде требуется подтвердить договоры API ЮKassa, Remnawave, Aeza, Timeweb, SMTP и Telegram, а также реальную выдачу доступа и настройку текущих VPN-нод. Критерии выпуска и незакрытые риски перечислены в [FINAL_REPORT.md](FINAL_REPORT.md).
