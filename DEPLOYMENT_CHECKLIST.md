## Резервная копия и первое обновление SQLite

1. Выбрать окно обслуживания. Заморозить изменение баланса и остановить все процессы приложения, внешний cron, таймер healthcheck и unit, обслуживающий ручные перезапуски. Оставшийся входящий webhook должен получать ответ, который допускает повтор доставки. Сохранить версию deployed-кода, nginx, unit-файлы и секреты в защищённом хранилище.
2. Снять онлайн-копию `.backup` по инструкции [DEPLOYMENT.md](DEPLOYMENT.md). Проверить `integrity_check` и отсутствие строк из `foreign_key_check`. Развернуть копию отдельным файлом и провести обновление сперва на ней.
3. Для базы, ранее управляемой через `db push`, создать пустой эталонный файл и загрузить только исходную SQL-схему. Проверить нулевую разницу схем рабочей копии и эталона через `prisma migrate diff --from-url ... --to-url ... --exit-code`. При расхождении сначала разобраться с отличиями схем. Для базы с действующей историей Prisma проверить `prisma migrate status`.
4. Для совпавшей базы без истории отметить применённой только исходную миграцию. Затем запустить `npm run prisma:deploy`. Для пустой базы достаточно `npm run prisma:deploy`. Сравнить количество пользователей, платежей, записей баланса и суммы по валюте с состоянием до миграции.

```bash
# Выполняется на изолированной копии.
umask 077
baseline_dir=$(mktemp -d)
sqlite3 "$baseline_dir/baseline.db" < prisma/migrations/20261123000100_baseline/migration.sql
npx prisma migrate diff --from-url "$DATABASE_URL" --to-url "file:$baseline_dir/baseline.db" --exit-code
npx prisma migrate resolve --applied 20261123000100_baseline
npm run prisma:deploy
```

5. Сверить исторические оплаты до включения трафика. Запрос ниже показывает кандидатов для ручной проверки по выгрузке магазина и проводкам. Не обнулять `creditedAt` массово. Исторические компенсации оформлять обычной проводкой администратора после сверки.

```sql
SELECT p.id, p.providerPaymentId, p.userId, p.amountKopeks
FROM Payment AS p
WHERE p.provider = 'yookassa' AND p.creditedAt IS NOT NULL
  AND NOT EXISTS (
    SELECT 1 FROM BalanceTransaction AS t
    WHERE t.userId = p.userId AND t.type = 'TOPUP'
      AND t.description = 'YooKassa payment ' || p.providerPaymentId
      AND t.amountKopeks = p.amountKopeks
  );
```

## Запуск, наблюдение и откат

- [ ] Поставить обновлённые unit-файлы и конфигурацию nginx. Проверить `nginx -t`, статус служб и действие healthcheck с действительным сертификатом. Запустить один экземпляр и проверить `GET /api/health`.
- [ ] Выполнить регистрацию и вход на стенде, проверить выдачу и копирование ссылки, оплату в тестовом магазине, сверку статуса, паузу/возобновление, лимиты устройств, бан и попытку открывать админку обычным пользователем. Подключить VPN-клиент на телефоне и ПК.
- [ ] Наблюдать за возрастом задач `User.vpnSyncAt`, неоплаченными проводками для подтверждённых заказов, ошибками очереди Telegram, `ORDER_UNCERTAIN`, временем фоновых циклов, свободным местом и ростом SQLite WAL. Сверить реальные интервалы и время доставки на стенде.
- [ ] Для `ORDER_UNCERTAIN` сверить имя ноды, историю заказов и счёт Aeza. После появления сервиса повторная сверка подхватит его. Повторную покупку разрешать только после явного подтверждения отсутствия принятого заказа у провайдера и фиксации решения.
- [ ] При отказе закрыть запись и остановить задачи. Сохранить новую БД, WAL и журналы изменений для сверки. Сначала оценить откат приложения на прежний артефакт поверх добавочной схемы на копии. Если нужна реставрация файла, использовать проверенную резервную копию и перед открытием трафика восстановить подтверждённые операции, возникшие после её создания.
- [ ] По результатам проверки истории Git перевыпустить обнаруженные ключи через кабинеты провайдеров. Обновить конфигурацию и проверить связь, затем отозвать старые ключи. Смена `NEXTAUTH_SECRET` завершает действующие сессии и инвалидирует выпущенные email-коды.
